# What `lawskills-hub` would lose by consuming this repository

- Checked: 2026-08-20
- Status: findings only; nothing here decides anything
- Scope: read both working trees. No build of `lawskills-hub` was run through
  `skills-hub-builder`, and no page was compared visually.

`lawskills-hub` is the hub this repository was abstracted out of, and adapting it
to consume `skills-hub` with no visible change to its published site is the
near-term test of the extraction. That adaptation is in progress in a separate
effort. This note records what reading the two trees says is still missing, so
whoever finishes it is not rediscovering the list.

## Sources

- `repos/lawskills-hub`: `scripts/build.py`, `scripts/build_actions.py`,
  `scripts/build_mcpb.py`, `templates/meta-skill.md`, `website/`, `skills/`,
  `CONTRIBUTING.md`, and the committed `_site/`.
- This repository: `packages/skills-hub-builder/src/skills_hub_builder/`,
  `hub.yaml`, `example/`.

## What already lines up

The inventory JSON is the same shape. `lawskills-hub/_site/inventory/cle.json`
and a file written by `packager.build_inventory` share the same keys — `group`,
`label`, `description`, `design`, `meta_skill`, `skills` — and the same per-skill
fields `name`, `description`, `install_url`, `version`, `status`, `source_path`.
`groups.json` matches likewise. Reading them side by side, the builder's inventory
code looks like a direct lift from `scripts/build.py`; that is an inference from
the shape, not from any recorded statement.

Page templates carry over without porting. The renderer loads templates from a
project's `website/` directory ahead of the bundled theme, and copies non-HTML
files from both. `lawskills-hub/website/` holds `_base.html`, `index.html`,
`install.html`, `css/`, `js/`, and `traces/`, so its pages and its trace viewer
can come across as project overrides rather than as builder features.

Trace data is already handled: `build.py` copies a project's `traces/` into
`_site/traces/` verbatim, which is where `lawskills-hub`'s viewer looks.

## What is missing

**Group metadata has no home.** `lawskills-hub` describes its five personas in one
`skills/personas.yaml`; the builder reads a `group.yaml` per group directory.
There are no `group.yaml` files in `lawskills-hub` (checked: zero). Discovery
would still find the five persona directories as groups, because a directory with
skills inside is a group regardless, but each would come out labelled from its
title-cased id with an empty description and no `design` block — so
`professor.json` would lose "Improve the quality of legal education" and
everything under it. The field mapping is also not one-to-one: the published
`cle.json` takes its `description` from the persona's `headline`, and folds
`pitch` into `design`. `GroupInfo` has no `headline` or `pitch`.

**Meta skill bodies would come out without their listings.** None of the five
`*-meta/SKILL.md` files contains a `{{ bundled_skills }}` placeholder (checked).
`lawskills-hub` assembles its meta bodies from `templates/meta-skill.md`, which
composes `{{frontmatter}}`, `{{intro}}`, `{{bundled_skills}}`, `{{assist_directly}}`,
and `{{extra_sections}}`. The builder only substitutes into a body that already
holds the placeholder. The zips would still bundle the sibling skills under
`references/<name>/subskill.md`; the router's body would simply never mention
them. Either the meta files gain the placeholder, or the builder gains the
template-composition step.

**`actions/` is not produced.** `lawskills-hub` publishes `actions/openapi.json`,
`actions/openapi.yaml`, `actions/personas.json`, `actions/personas/`, and
`actions/skills/`, generated by `scripts/build_actions.py`. Nothing in this
repository writes them; `outputs.gpt_actions` is a parsed flag with no reader.
`lawskills-hub`'s README describes this API as the mechanism a Custom GPT uses to
discover and load skills as an Action, so these are addresses something outside
the repository depends on, not just files on the site.

**`packages/mcpb/` is not produced.** Generated by `scripts/build_mcpb.py` from
`templates/mcpb`. `outputs.claude_extension` is likewise a flag with no reader.
Per `lawskills-hub`'s README the `.mcpb` packages an MCP server that fetches
skills from the same static API, so it depends on the `actions/` gap above.

**Frontmatter style is fragile rather than broken.** The builder splits
frontmatter lines on the first colon instead of parsing YAML. All 19 `SKILL.md`
files in `lawskills-hub` use single-line values, and nested `metadata: / version:`
survives because indentation is stripped, so today's files parse correctly.
But `CONTRIBUTING.md` shows `description: >` in its worked example, and that form
yields the description `">"`. A contributor following the guide would produce a
skill that lists as `">"` on the site.

## Open questions

- Should `actions/` and `packages/mcpb/` be ported into the builder behind the
  existing flags, or stay in `lawskills-hub` as extra build steps? Porting them
  makes the flags real for every hub; leaving them keeps GPT- and Claude-specific
  packaging out of shared infrastructure.
- Should the builder read a project-level `personas.yaml`-style file as an
  alternative to per-directory `group.yaml`, or should `lawskills-hub` split its
  file into five? Splitting loses a single readable roster of personas.
- `headline` and `pitch` have no equivalent in `GroupInfo`. Extend the schema, or
  ask consumers to fold them into `description` and `design`?

## Addendum, 2026-08-20 (later the same day): built and compared

- Checked: 2026-08-20, after the gaps above were closed
- Status: measured, not deployed
- Method: `lawskills-hub` was built twice with the same URLs
  (`--base-url https://harvard-lil.github.io/lawskills-hub/`,
  `--repo-url https://github.com/harvard-lil/lawskills-hub/`) — once with its own
  `scripts/build.py` before the adaptation, once with `skills-hub-builder` after
  it — and the two `_site/` trees compared file by file.

The findings above are no longer open questions. `actions/` and `packages/mcpb/`
were ported into the builder behind the existing flags; `lawskills-hub` split its
`personas.yaml` into five `group.yaml` files, mapping `headline` to the group
`description` and folding `pitch` into `design`; the meta skill bodies come from
the consumer's `templates/meta-skill.md`.

### What matches

Both trees hold 219 files, 218 of them shared. 36 are byte-identical:
`index.html`, `install.html`, both CSS files, `traces/index.html`, all 14
non-meta `.skill` zips, and 17 of the 25 files under `actions/`.

Another 166 match on content but not on bytes, for reasons that are not
regressions:

- The five meta `.skill` zips have identical member lists and identical member
  bytes. The one differing byte range is the zip entry timestamp on the generated
  `SKILL.md`, which both generators write with `writestr` — so two runs of the old
  scripts differed the same way.
- All 160 trace files and `traces/index.json` match after `"persona"` is renamed
  to `"group"`, which is the schema migration `skill-eval` requires and which was
  applied to the repository's committed traces.

That leaves 16 files genuinely different.

### What differs, and why

**Group ordering (8 files).** `actions/personas.json`, `actions/openapi.json`,
`actions/openapi.yaml`, and the two rendered markdown files inside the `.mcpb`
list groups alphabetically where the old build listed them in `personas.yaml`
order. Checked: the JSON is equal once compared by id rather than by position,
every OpenAPI `enum` is equal once sorted, and the two markdown files are equal
as line multisets. The site itself is unaffected — `js/app.js` pins display order.

**`design.pitch` (5 files).** `actions/personas/*.json` are equal to the baseline
once `design.pitch` is dropped from the new files. `group.yaml` nests `pitch`
under `design`; `personas.yaml` had it as a sibling, and the old script published
the sibling only.

**Deliberate changes, not regressions (7 files).** `inventory/groups.json`
replaces `inventory/personas.json`, the five per-group inventories use `group`
and `description` where the old ones used `persona`, `headline` and `pitch`, and
`js/app.js` and `js/traces.js` carry the hand-edits that read the new shapes.

### Not established

The site has not been deployed through `.github/workflows/build-and-deploy.yml`.
No Custom GPT has been pointed at the generated `actions/openapi.yaml`, and no
Claude Desktop has installed `legal-ed-skills-hub.mcpb`. Both are compared
against a previous generator's output, which is evidence that nothing was lost in
the port, not evidence that either client works.
